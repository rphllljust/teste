# CISNE ERP — 16-step operational flow / GO evidence and acceptance

This document is a **release gate**, not a declaration that a build equals
business acceptance. Code is staged in the existing
`fix/cisne-hml-parallel-audit-20261127` branch. Production is out of scope.

## Reference workflow

| # | Acceptance evidence | Owner/operator boundary |
|---|---|---|
| 1 | Channel, source reference and contact are captured in `svc_needs` | Verified owner creates |
| 2 | Proposal, contract, PO/RC and authorization references in `svc_needs` / `svc_commercial_documents` | Owner-only commercial information |
| 3 | Intake event `received`, request hash, tenant and actor audit | Verified owner only |
| 4 | `start_analysis` with state and owner verification | Verified owner |
| 5 | `approve` / `reject` with reason and financial snapshot | Verified owner |
| 6 | `convert` creates canonical `service_orders.status=draft` | Verified owner |
| 7 | `set_plan` preserves lines and resource categories | Verified owner, immutable after release |
| 8 | `svc_commercial_price_lines`, terms versions and global/itemized pricing | Financial fields never sent to employee inbox |
| 9 | OS authorized via canonical command; `release` gated on plan and commercial limits | Verified owner |
| 10 | Employee binding in `svc_employee_links` plus assignment | Verified owner; tenant member required |
| 11 | `employee-inbox` returns only operational data and assigned needs | Authenticated linked employee |
| 12 | Persisted assigned/viewed/received events, one per assignment | Assigned employee only |
| 13 | Employee start atomically transitions need and OS; generic start cannot bypass receipt | Employee with acknowledged assignment |
| 14 | Field lines, pauses, resumes, meter readings, field events and protected files | Assigned employee |
| 15 | Planned lines preserved while actual lines append; no silent overwrite | Immutable actuals |
| 16 | Additional request by employee; accept/reject by verified owner with justification and audit | No employee price or self-approval |

## Database and evidence

* `0034_service_need_to_execution`: workflow and audit foundation.
* `0035_service_ops_enterprise_commercial_field`: terms, price versions,
  commercial documents, field events, additional requests and decisions.
* `0036_cisne_individual_auth_and_evidence`: explicit personal identities,
  persistent login throttling and immutable protected binary evidence.
* `0037_service_plan_revision_and_acceptance`: immutable versioned plans,
  employee completion report, administrative return/accept decision and
  atomic linked OS transition to `completed` without auto-invoicing.
* Small evidence files are persisted in PostgreSQL under `tenant_id + need_id`.
  Accepted PDF/JPEG/PNG/WebP up to 4 MiB/file, 100 files and 64 MiB per need;
  upload validates magic bytes, download rechecks authorization and SHA256.
  No URL or credential from MinIO/NextCRM is exposed to the browser. This does
  not replace enterprise antivirus, lifecycle retention, object-store
  replication or a complete document management system.

## Staging identity cutover (required for full GO)

The default `CISNE_STAGING_ACTOR_ID` remains a **single shared identity**.
It cannot validate that two owners and an employee each signed in separately.

1. Using approved staging database access, verify that both declared owner
   records are attached to distinct actor IDs with `identity_state=verified`,
   and both have active owner memberships in the correct enterprise tenant.
2. Link each employee actor to an active operator membership and professional
   record using the existing owner-controlled employee-link command.
3. An authorized operator executes
   `scripts/provision-cisne-individual-login.mjs` with explicit staging
   environment guard, actor, login, and passphrase supplied by secure stdin.
   Do **not** put passwords in git, command-line arguments, reports or logs.
   The script refuses unverified owners, unlinked employees and duplicates.
4. Only **after** provisioning, enable the Railway staging variable
   `CISNE_STAGING_AUTH_MODE=individual`. This disables all legacy v1 shared
   login cookies (fail closed) and enables personal v2 signed 30-minute cookies.
5. Reauthenticate Abrahim, Rafael and each employee **separately** through
   `/staging-login`. Test positive and negative tenant, commercial, order,
   attachment and additional-decision permissions from each real account.
6. Read `/api/enterprise/tenants/{tenantId}/service-needs/readiness` as a
   verified owner. It must return `READY_FOR_PERSONAL_UAT`; this is still not
   a business GO by itself. Record real acceptance separately.

**Never flip the authentication mode before credentials are enrolled**:
doing so intentionally rejects all shared sessions. No actor IDs or passwords
are autogenerated to impersonate the actual owners.

## Release evidence required

* GitHub CI: full application build, domain contracts, real PostgreSQL 16/18
  handlers, independent PostgreSQL-only gate and backup/restore rehearsal.
* Railway: staging deploy `SUCCESS`, `/api/health/ready` succeeds, no
  runtime crashes, migration ledger includes 0034, 0035, 0036 and 0037.
* Authentic browser run: two declared owners with distinct sessions and a
  linked employee test an entire service need from intake to additional
  approval. Include deliberate denial of price access for the employee.
* Upload a small real non-sensitive test PDF/image, download it with authorized
  owner and employee (field only), verify denial for the wrong tenant, and
  compare checksum.
* Final human operational acceptance, with exact date, scope, actors and
  deployment SHA. **Do not claim production GO based only on synthetic CI.**

## Current open external dependencies

* Real owner/employee credentials and actor mapping are an operational
  provisioning step; automation must not invent them.
* Large-file or regulated document archival, malware scanning, backup/PITR
  coverage, retention rules and fiscal billing integrations are distinct
  enterprise release workstreams.
* Production login currently uses a single production actor; its separation
  from staging must remain intact. Personal staging identity is not an
  authorization to promote automatically to production.

## Acceptance extension: returning and completing an execution

The operational plan is a versioned set, not a mutable record with no history.
The two verified controllers can replace the working projection only while
`svc_needs.status=converted`. Every subsequent version requires a reason;
all versions are immutable and retain the approving actor and exact resource
quantities. The employee's work report records the exact plan version and
actual line snapshot at submission. No commercial price fields are exposed.

After execution is recorded, only the assigned employee may submit a work
report. This is blocked while the operation is paused or an additional awaits
administrative decision. The need enters `review_pending` and prevents any
new quantity or event. One of the two verified owners reviews the latest
report and returns it with a reason to continue execution, or accepts it:
`svc_needs.status=completed` and canonical
`service_orders.status=completed` are updated atomically. The generic
OS `complete` and `cancel` commands are denied for linked needs.
Only a separately governed measurement can follow an accepted report;
there is no automatic billing or fiscal integration.
